# 歷史分群

用 git 歷史算出 rc4 每個檔案的「誕生日」,把現在的程式碼依時期分群,看專案是怎麼一層一層長出來的。

## 怎麼算

- 資料來源:官方 repo 從 `v0.8.8-rc4` 標籤往回的 5737 個提交。
- 方法:依時間順序讀 `git log --name-status -M`,記錄每個路徑第一次出現的日期。檔案被改名或搬動時(`-M` 改名偵測),誕生日沿用舊路徑的。
- 範圍:rc4 的 `api/`、`client/src/`、`packages/*/src/` 下的非測試程式碼檔,共 3036 個,每個都找得到誕生日。
- 意義:**誕生日是這個檔案路徑第一次出現的日期**,不是這個功能誕生的日期。檔案內容多年來一直被修改。

## 分群總表

「新增」是該時期誕生、至今仍存在的檔案。「主要內容」是依目錄名稱判斷,沒有逐一讀過檔案。

| 時期 | 新增 | 累計 | 期間的 release | 主要內容 |
|---|---|---|---|---|
| P1 2023-03 以前 | 64 | 64 | v0.0.1 到 v0.2.0 | 對話應用的骨架:後端路由(6)、資料庫連線(2)、前端狀態儲存(5)、對話列表與訊息元件 |
| P2 2023-04 到 06 | 66 | 130 | v0.3.0 到 v0.5.2 | 登入與驗證(前端 Auth 7、後端 strategies 6)、AI 客戶端(`app/clients` 6)、外掛 |
| P3 2023-07 到 12 | 250 | 380 | v0.5.3 到 v0.6.5 | 對話介面成形(Chat 35、Input 18)、模型端點(14)、後端中介層(14)、`data-provider` 誕生(14) |
| P4 2024-01 到 06 | 390 | 770 | v0.6.6 到 v0.7.3 | 側邊面板(37)、檔案(24)、提示詞(19)、後端服務(31) |

## 各層的誕生時間

| 層 | 最早的檔案 | 大量誕生的時期 |
|---|---|---|
| `api/` | 2023-03(12 個) | 2023 到 2024(到 2024 年底累計 231 個,占 rc4 的 62%) |
| `client/src/` | 2023-03(20 個) | 2024 到 2026(173 個在 2023 年底前,其餘約 1245 個之後誕生) |
| `packages/data-provider` | 2023-07 | 2023 到 2024(到 2024 年底累計 29 個,rc4 共 65 個) |
| `packages/data-schemas` | 2023 起有零星檔案 | **2025 上半年**(約 90 個,模型抽出來的時期) |
| `packages/api` | 2023 起有零星檔案 | **2025 下半年到 2026**(約 670 個) |
| `packages/client` | 圖示與元件早期就有 | 2023 到 2024(圖示檔 `svgs` 約 80 個) |

`packages/` 底下早期誕生的檔案(例如 `packages/client/svgs`),是因為檔案後來從 `client/` 搬過去,誕生日沿用原路徑。這和[專案建立順序](build-order.md)提到的「`packages/` 是後來抽出來的」一致。

## 這對學習設計的意義

**每個檔案都有明確的階段。** 階段的順序可以直接用誕生日分群,說明文件能寫「這批檔案是 2023-04 到 06 誕生的,當時的 release 是 v0.3.0 到 v0.5.2」,不用靠功能分類去猜。

**但不能直接拿「早期誕生的檔案」當 MVP。** 這些檔案現在已經 import 了幾乎整個專案:

| 保留誕生日 ≤ | 保留的檔案 | 補齊相依後(後端 / 前端) | 要刪的 import | 涉及檔案 | 保留檔案的 import 總數 |
|---|---|---|---|---|---|
| 2023-03-31 | 64 | 356 / 1332 | 197 | 43 | 220 |
| 2023-06-30 | 130 | 359 / 1335 | 308 | 84 | 391 |
| 2023-12-31 | 380 | | 717 | 175 | 1382 |
| 2024-06-30 | 771 | | 866 | 288 | 2590 |
| 2025-12-31 | 1661 | | 1062 | 400 | 5138 |

「補齊相依後」是只取該時期以前誕生的檔案當起點,追蹤它們 import 的所有檔案,結果是整個後端與整個前端。所以如果硬要只留早期檔案,要在這些檔案裡刪掉對較晚誕生檔案的 import(上表「要刪的 import」),保留 64 個檔案就要刪 197 條,**這些檔案會被刪得只剩骨架**。

## 限制

- 誕生日是路徑的誕生日。檔案若被改寫、改名時內容變動太大(超過改名偵測的相似度門檻),會被當成新檔案。
- 舊檔案常被較晚誕生的新檔案取代(例如登入的實作),所以早期檔案本身不一定能湊成一個今天能跑的整體。
- 「主要內容」依目錄名稱判斷,沒有逐一讀過檔案,正式寫入階段文件前要逐項核對。
- 各層的檔案數是非測試程式碼檔,不含設定檔、樣式、翻譯檔與圖片。
